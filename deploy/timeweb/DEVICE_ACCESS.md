# Доступ к VR Catalog по сертификатам устройств

Защита устанавливается на внешнем HTTPS Nginx. Nginx проверяет клиентский
сертификат по доверенному центру, затем сверяет его SHA-256 с реестром VR
Catalog. Запись должна быть активной, действующей и незаблокированной. Проверка
выполняется для каждого браузерного запроса, включая статику и API. Для
изменений во вкладке «Доступы» также нужны админская сессия и CSRF-токен.

## Подготовка

1. Выделите отдельный центр для VR Catalog. Используйте отдельный ключ,
   независимый от ключа TLS-сервера и ключей Sales Journal. При наличии PKI
   храните корневой ключ вне приложения и выдайте отдельный подписывающий
   промежуточный сертификат. Файлы `issuer.crt` (публичный сертификат подписанта в PEM) и
   `issuer.key` (его закрытый ключ в PEM) разместите
   в защищённой директории вне репозитория. Ключ должен быть доступен только
   администратору хоста и пользователю backend (UID 10001 в образе).
2. Добавьте `DEVICE_CA_DIRECTORY` и уникальный случайный
   `DEVICE_PROXY_SECRET` (от 32 символов) в закрытый файл окружения. Создайте
   файл `/etc/nginx/vrcatalog-device/proxy-secret.conf` с директивой
   `proxy_set_header X-VR-Device-Secret "<значение DEVICE_PROXY_SECRET>";`.
   Секрет должен совпадать в двух конфигурациях. Ограничьте права файла
   и не выводите эти значения в журналы.
3. В закрытом файле окружения проекта задайте
   `COMPOSE_FILE=docker-compose.yml:deploy/timeweb/device-access.compose.yml`,
   чтобы systemd и скрипт обновления тоже использовали оба файла Compose.
   Запустите миграции существующей базы
   (образ делает это при старте):

   ```bash
   docker compose -f docker-compose.yml -f deploy/timeweb/device-access.compose.yml up -d --build
   ```

   Backend остаётся без опубликованного порта, frontend слушает только
   loopback. Сохраните эту топологию: внешние клиенты должны обращаться
   через HTTPS Nginx.

## Первое устройство и конфигурация Nginx

1. Пока HTTPS-маршрут закрыт на обслуживание, зарегистрируйте первое
   устройство на сервере. Передайте публичный CSR устройства на вход
   команды, а полученный сертификат верните владельцу:

   ```bash
   docker compose -f docker-compose.yml -f deploy/timeweb/device-access.compose.yml exec -T backend \
     python -m app.cli.device_access --name 'Ноутбук администратора' --owner 'Администратор' \
     < first-device.csr > first-device.crt
   ```

   Для уже подписанного клиентского сертификата добавьте `--register`
   и передайте его вместо CSR. Подготовьте второе устройство
   администратора для восстановления доступа.
2. После регистрации первого устройства выпускайте следующие сертификаты
   во вкладке «Настройки → Доступы». Для аппаратно привязанного устройства
   остаётся CLI с публичным CSR, созданным неизвлекаемым ключом.
3. Скопируйте `device-access.upstream.conf` в
   `/etc/nginx/vrcatalog-device/upstream.conf`. В действующем HTTPS
   `server` настройте `ssl_client_certificate` на цепочку доверия для
   клиентских сертификатов и `ssl_verify_client optional`. Если HTTPS
   хост уже использует клиентские сертификаты для других приложений,
   согласуйте существующую цепочку и глубину проверки. Учитывайте, что
   запрос клиентского сертификата задаётся для всего HTTPS-хоста.
4. Замените текущие location для `/vr/catalog` и `/vr/catalog/`
   (включая отдельный location экспорта) директивами из
   `device-access.locations.conf`. HTTP должен только перенаправлять
   на HTTPS. Проверьте `nginx -t` и перезагрузите конфигурацию.
5. Проверьте, что без сертификата, с доверенным незарегистрированным и
   заблокированным сертификатом каталог и его браузерный API возвращают
   отказ, а зарегистрированное устройство открывает каталог. Проверьте
   также вход администратора и запросы Sales Journal с его токеном.

Маршруты `/api/integration/` и `/api/internal/` под префиксом каталога
сохраняют межсервисную авторизацию на backend. Если интеграция обращается
к прежнему `/api/products?property=…&property_value=…`, ей потребуется
зарегистрированный сертификат либо переход на API из пространства
`/api/integration/`.

При блокировке или перевыпуске старый отпечаток остаётся в реестре и
отклоняется при следующем запросе. Операции с устройствами выполняйте
из второго разрешённого устройства, если текущее нужно заменить или
заблокировать.


## Выпуск и установка в Windows

Во вкладке «Доступы» укажите устройство и владельца, при необходимости комментарий.
Сервер генерирует пароль из 32 латинских букв и цифр через Python `secrets`,
создаёт ключ RSA 3072,
подписывает клиентский сертификат существующим центром и отдаёт
зашифрованный PKCS#12 с ключом, сертификатом и публичным сертификатом
подписанта. Сервер хранит только публичные реквизиты и состояние
сертификата. Файл повторно получить нельзя. Не передавайте пароль вместе
с файлом и не помещайте их в общую папку.

В Windows откройте файл `.p12`, выберите «Текущий пользователь»,
введите пароль, оставьте экспорт закрытого ключа выключенным и
импортируйте в хранилище «Личное». В `certmgr.msc` проверьте, что
сертификат появился в «Личное → Сертификаты» и имеет закрытый ключ.
Перезапустите браузер, если он сохранил выбор старого сертификата.
Доверие к цепочке устанавливайте по правилам вашей организации.

При подготовке замены новый сертификат появляется в списке как ожидающий,
а старый сохраняет доступ. Сохраните и установите новый файл, затем
подтвердите замену со второго разрешённого устройства. Пока сертификат
ожидает активации, открыть каталог с ним нельзя. Подтверждение оператора
проверяет только его явное согласие; TLS-владение новым ключом до активации
не проверяется. Автоматическая проверка потребовала бы отдельного
ограниченного маршрута HTTPS для предъявления ожидающего сертификата.
Если файл потерян или не подходит, отмените замену и подготовьте другую.

При подтверждении старый сертификат отзывается в базе одновременно с
активацией нового. После этого запрашивается публикация CRL через текущий
Unix-сокет. Если публикация не подтверждена, новые состояния сохраняются
и старый сертификат отклоняется реестром. Повторите подтверждение со
второго разрешённого устройства, чтобы повторить только публикацию CRL.
При отдельной блокировке уже отозванного сертификата повторный вызов
административного маршрута блокировки также повторяет публикацию.

## Обновление с 0029 и откат

1. Сохраните резервную копию реестра и проверьте доступ со второго
   администраторского устройства. Сохраните текущий CA, настройки TLS,
   секрет прокси и сокет CRL. Не перевыпускайте действующие сертификаты.
2. Проверьте конфигурации внешнего и контейнерного Nginx. Для префикса
   `/vr/catalog/api/access/devices/` обе конфигурации отключают буферизацию
   запроса, ответа и кэш, чтобы Nginx не записывал пароль и PKCS#12 во
   временные файлы. Во внешнем Nginx перенесите только новый блок префикса,
   сохранив существующие TLS, CRL и `auth_request`. Проверьте, что логи,
   трассировка и дополнительные прокси не записывают тела этих запросов.
3. В окно обслуживания обновите backend с миграцией
   `0030_device_pkcs12_replacement`, затем frontend. Проверьте, что старый
   сертификат открывает каталог, а подготовленный отклоняется до
   подтверждения. Для пробного перевыпуска используйте отдельное тестовое
   устройство. Старые веб-клиенты требуют обновления страницы для выпуска
   и перевыпуска; их CSR-запросы возвращают ошибку без изменения доступа.
4. Для отката сначала закройте доступ на обслуживание и остановите
   приложение. Текущим образом выполните
   `alembic downgrade 0029_device_certificate_serial` в одноразовом
   контейнере backend. Миграция помечает неактивированные сертификаты
   отозванными до удаления полей, поскольку старая проверка не различает
   статус ожидания. Сохраните отзыв старых сертификатов после уже
   подтверждённых замен. Запустите прежние версии backend и frontend
   и опубликуйте актуальный CRL существующим сервисом, затем проверьте
   доступ и снова откройте маршрут.

Автоматический выпуск создаёт переносимый ключ. После импорта в Windows
исходный файл .p12 остаётся копией ключа, пока существует. Если требуется
аппаратная привязка, используйте выпуск через CLI с CSR от неизвлекаемого
ключа. Текущий механизм проверки сравнивает сертификат с реестром, а не
подтверждает, что ключ находится в TPM.


## Обновление автоматической выдачи пароля на FirstVDS

Эта доработка не требует миграции поверх `0030_device_pkcs12_replacement`.
Не выполняйте downgrade базы при откате только этой доработки.

1. Сохраните версии образов backend/frontend и резервную копию реестра.
   Проверьте второе разрешённое администраторское устройство. Не меняйте
   production CA, Windows-01, TLS, CRL, секреты прокси и действующие сертификаты.
2. Проверьте доработку на тестовом стенде с отдельным тестовым CA. После
   ручного согласования обновления установите backend и frontend одной версии.
   Проверьте `nginx -t` контейнерного Nginx и наличие точного location
   `/vr/catalog/api/access/devices` без завершающего слеша: он должен проксировать
   запрос без 301/307. Внешний Nginx этой доработкой не изменяется.
3. Перезагрузите страницу администратора: старый интерфейс с ручным паролем
   больше не совместим с контрактом выпуска и получит 422 без выпуска сертификата.
   Существующие сертификаты продолжают работать. Проверьте список устройств и,
   если требуется, выпуск отдельного тестового устройства, не Windows-01.
4. При откате верните одновременно предыдущие образы backend и frontend,
   сохранив текущую базу, CA и конфигурацию CRL; обновите страницу браузера.
   Не отменяйте уже выполненные отзывы и активации сертификатов.

Ответ выпуска — JSON с `device`, `filename`, `pkcs12_base64`, `password`;
заголовок `Cache-Control: no-store`. Пароль и файл доступны только в текущем
окне: скачивание его не закрывает, любое закрытие требует подтверждения.
После подтверждения ссылки Blob отзываются, ссылки на секреты в состоянии
удаляются. Гарантировать обнуление неизменяемых Python/JavaScript-строк нельзя.
Скопированный пользователем пароль остаётся в системном буфере обмена;
приложение не очищает чужое содержимое буфера автоматически. Не включайте
запись тел запросов/ответов в прокси, APM, сетевых дампах и клиентской аналитике.

Frontend отправляет случайный `operation_id` из 32 hex-символов и сохраняет
его для повторной попытки в пределах формы. Backend сериализует одинаковые
операции транзакционной advisory-блокировкой PostgreSQL (SQLite: BEGIN IMMEDIATE).
Хеш операции записывается как CN нового сертификата с учётом лимита X.509;
в этом поле нет пароля. Проверка повторов сохраняется после перезапуска.
Уже завершённый запрос возвращает 409 без повторной выдачи пароля или файла.
При потере ответа проверьте список устройств. Если файл/пароль потеряны,
явно заблокируйте новый сертификат либо отмените ожидающую замену и только
затем начните новую операцию. Автоматического повторного выпуска нет.
Старый сертификат при подготовке замены действует до отдельного подтверждения.
