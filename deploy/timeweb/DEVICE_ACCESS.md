# Доступ к VR Catalog по сертификатам устройств

Защита устанавливается на внешнем HTTPS Nginx. Nginx проверяет клиентский
сертификат по доверенному центру, затем сверяет его SHA-256 с реестром VR
Catalog. Запись должна быть действующей и незаблокированной. Проверка
выполняется для каждого браузерного запроса, включая статику и API. Для
изменений во вкладке «Доступы» также нужны админская сессия и CSRF-токен.

## Подготовка

1. Выделите отдельный центр для VR Catalog. Используйте отдельный ключ,
   независимый от ключа TLS-сервера и ключей Sales Journal. При наличии PKI
   храните корневой ключ вне приложения и выдайте отдельный подписывающий
   промежуточный сертификат. Файлы `issuer.crt` (публичный сертификат подписанта в PEM) и
   `issuer.key` (его закрытый ключ в PEM) разместите
   в защищённой директории вне репозитория. Ключ должен быть доступен только
   администратору хоста и пользователю backend (UID 10001 в образе).
2. Добавьте `DEVICE_CA_DIRECTORY` и уникальный случайный
   `DEVICE_PROXY_SECRET` (от 32 символов) в закрытый файл окружения. Создайте
   файл `/etc/nginx/vrcatalog-device/proxy-secret.conf` с директивой
   `proxy_set_header X-VR-Device-Secret "<значение DEVICE_PROXY_SECRET>";`.
   Секрет должен совпадать в двух конфигурациях. Ограничьте права файла
   и не выводите эти значения в журналы.
3. В закрытом файле окружения проекта задайте
   `COMPOSE_FILE=docker-compose.yml:deploy/timeweb/device-access.compose.yml`,
   чтобы systemd и скрипт обновления тоже использовали оба файла Compose.
   Запустите миграции существующей базы
   (образ делает это при старте):

   ```bash
   docker compose -f docker-compose.yml -f deploy/timeweb/device-access.compose.yml up -d --build
   ```

   Backend остаётся без опубликованного порта, frontend слушает только
   loopback. Сохраните эту топологию: внешние клиенты должны обращаться
   через HTTPS Nginx.

## Первое устройство и конфигурация Nginx

1. Пока HTTPS-маршрут закрыт на обслуживание, зарегистрируйте первое
   устройство на сервере. Передайте публичный CSR устройства на вход
   команды, а полученный сертификат верните владельцу:

   ```bash
   docker compose -f docker-compose.yml -f deploy/timeweb/device-access.compose.yml exec -T backend \
     python -m app.cli.device_access --name 'Ноутбук администратора' --owner 'Администратор' \
     < first-device.csr > first-device.crt
   ```

   Для уже подписанного клиентского сертификата добавьте `--register`
   и передайте его вместо CSR. Подготовьте второе устройство
   администратора для восстановления доступа.
2. На устройстве создайте ключ и CSR. Где возможно, используйте
   неизвлекаемый ключ в системном или аппаратном хранилище. В интерфейс
   передаётся только CSR или публичный сертификат. После выпуска скачайте
   сертификат и установите его в хранилище устройства с исходным ключом
   и цепочкой центра. Экспортируемый ключ можно скопировать на другое
   устройство, поэтому для аппаратной привязки нужен неизвлекаемый ключ
   и соответствующая политика выдачи.
3. Скопируйте `device-access.upstream.conf` в
   `/etc/nginx/vrcatalog-device/upstream.conf`. В действующем HTTPS
   `server` настройте `ssl_client_certificate` на цепочку доверия для
   клиентских сертификатов и `ssl_verify_client optional`. Если HTTPS
   хост уже использует клиентские сертификаты для других приложений,
   согласуйте существующую цепочку и глубину проверки. Учитывайте, что
   запрос клиентского сертификата задаётся для всего HTTPS-хоста.
4. Замените текущие location для `/vr/catalog` и `/vr/catalog/`
   (включая отдельный location экспорта) директивами из
   `device-access.locations.conf`. HTTP должен только перенаправлять
   на HTTPS. Проверьте `nginx -t` и перезагрузите конфигурацию.
5. Проверьте, что без сертификата, с доверенным незарегистрированным и
   заблокированным сертификатом каталог и его браузерный API возвращают
   отказ, а зарегистрированное устройство открывает каталог. Проверьте
   также вход администратора и запросы Sales Journal с его токеном.

Маршруты `/api/integration/` и `/api/internal/` под префиксом каталога
сохраняют межсервисную авторизацию на backend. Если интеграция обращается
к прежнему `/api/products?property=…&property_value=…`, ей потребуется
зарегистрированный сертификат либо переход на API из пространства
`/api/integration/`.

При блокировке или перевыпуске старый отпечаток остаётся в реестре и
отклоняется при следующем запросе. Операции с устройствами выполняйте
из второго разрешённого устройства, если текущее нужно заменить или
заблокировать.


### Пример для устройства с OpenSSL

Если на устройстве доступен только файловый ключ, создайте его и запрос
локально. Передайте администратору только `device.csr`:

```bash
umask 077
openssl req -new -newkey ec -pkeyopt ec_paramgen_curve:P-256 \
  -subj '/CN=VR Catalog device' -keyout device.key -out device.csr
```

Для браузера, который импортирует PKCS#12, соберите установочный файл
на том же устройстве из полученного сертификата, исходного закрытого
ключа и публичной цепочки центра:

```bash
openssl pkcs12 -export -inkey device.key -in device.crt \
  -certfile issuer-chain.pem -out device.p12
```

Установочный файл содержит закрытый ключ. Храните его только на этом
устройстве и удалите после импорта, если резервная копия не предусмотрена
вашей политикой. Для аппаратной привязки используйте CSR, созданный
ключом из TPM или неизвлекаемого хранилища, и установку сертификата
средствами этой платформы.
